# Gotchas — LD4, LD5, LD6, LD7, LD8 (dynamic-round-pipeline)

> Scope: ONLY what the original findings MISSED. No re-analysis of the topic.
> Evidence cites verifier-loop repo files + the LD turn files.
> Severity rank: 1=YAGNI, 2=Minor, 3=Moderate, 4=Significant, 5=Sophisticated.

---

## Rank 4 — Significant (gaps that change the design or break an invariant)

### G4.1 — LD4: PL-D ↔ PL-E oscillation loop (no escape clause) [LD4]
The esca lifecycle (turn4 / open-threads OT2) resets esca to 0 on ANY Mixed/Final
reject. So a goal can loop forever:
`Gate-pass → Confirm-reject (esca=1) → … → (esca=2) → PL-E Mixed → reject (esca=0)`
→ back to PL-D → re-escalate → PL-E → reject → reset …
There is NO cap on total escalation cycles and NO "give up / hard-fail" exit.
A persistently-broken goal burns verifier turns indefinitely across RESUMEs.
- Evidence: `flow/findings/2026-07-20-dynamic-round-pipeline/2026-07-20-turn4-rename-esca.md`
  (esca lifecycle: `Mixed reject → esca = 0`); no max-cycle field in config schema.
- Mitigation: add `escaMaxRetries` (or reuse a global round cap); after N PL-E↔PL-D
  cycles without progress, hard-fail the goal instead of looping.

### G4.2 — LD4: "Mixed unanimous pass" contradicts configurable n [LD4]
LD4 text says "After Mixed **unanimous** pass, still require one more smart".
turn3 derives Mixed threshold = `n` (preserves threshold n), NOT unanimity.
For `n=1, m=2`: Mixed = 1D+1S, passes on a single APPROVE → the lone smart
verifier can pass Mixed alone (1S approve, 1D reject). That defeats Mixed's
intent ("both dump AND smart agree") and makes the subsequent Final pure
redundancy (smart already voted yes in Mixed).
- Evidence: LD4 verbatim ("unanimous") vs
  `2026-07-20-turn3-dynamic-generic.md` ("Mixed … threshold: n").
- Mitigation: either (a) lock Mixed threshold = m (true unanimity), or (b) drop
  "unanimous" from LD4 and state threshold = n explicitly, accepting the n<m
  degenerate case.

### G4.3 — LD4: Mixed can pass on smart-alone when n < ceil(m/2) [LD4]
Consequence of G4.2 stated concretely. For m=3, n=1: Mixed = 1D+2S, passes on
1 approve. Either smart alone (1S) passes → Final is redundant. The pipeline
shape the user drew ("1/2 smart, 1/2 dump, round up") assumes n forces BOTH
roles to agree, which only holds when n > max(dump_count, smart_count). That
invariant is never stated or enforced.
- Evidence: turn3 Mixed table (m=3 → 1D+2S); no `n > max(dump,smart)` rule.
- Mitigation: config-validate `n > ceil(m/2)` for PL-E, or document that Mixed
  degrades to smart-only when n ≤ ceil(m/2).

### G5.1 — LD5: round-recovery STATUS/RECOVER assume one round = m uniform slots [LD5]
Verdict path is `rounds/<round>/<verifierId>/` (src/verdict/mod.rs:137-142).
LD5 + LD3 put ALL sub-phases of one invocation under the SAME top-level round
(1a,1b,1c,1d share round=1). LD16 then writes d1,d2,s1,s2,… all under
`rounds/1/`. `round_recover::status` (LD7, src/round_recover/mod.rs) reports
slot count and null/non-null per round assuming uniform m slots. With the
pipeline, round 1 has `m + k + (escalation: m + k)` slots — the status probe
will misreport the round as "incomplete" or "decided" because it cannot tell
which phase the slots belong to. RECOVER's "harvest in-flight verdict" logic
also can't tell a half-written Gate slot from a half-written Confirm slot.
- Evidence: `src/verdict/mod.rs:137-142` (slot path keyed on round only);
  `src/round_recover/mod.rs:176-184` (status reads current_round's slots);
  LD3 (sub-rounds under one round) + LD16 (d/s prefixed ids).
- Mitigation: add a `phase` dimension to the slot path
  (`rounds/<round>/<phase>/<vid>/`) and a `currentPhase` field to state.json;
  teach status/RECOVER to report per-phase. Otherwise RECOVER is unsafe under
  the pipeline.

### G5.2 — LD5: GoalLock held for entire multi-phase pipeline [LD5]
`GoalLock::acquire_exclusive` (round_recover LD5, src/round_recover/mod.rs:83)
is held for the full duration of NEW/RESUME/RECOVER. Single-cmd pipeline
(LD5) = Gate(m) + Confirm(k) [+ Mixed(m) + Final(k)] all under one lock. With
`verifierTimeoutSec=1800` (src/store/config.rs default) and worst-case
escalation, that is hours of exclusive lock. A second process calling
`jewilo RECOVER <goalId>` on a stuck pipeline is blocked the entire time —
recovery is supposed to be the escape hatch for stuck verifiers, but the lock
makes it impossible to intervene.
- Evidence: src/round_recover/mod.rs:54-109 (GoalLock held for full cmd);
  config default verifierTimeoutSec=1800.
- Mitigation: release+reacquire the lock between phases (each phase is a
  natural breakpoint), or add a force-recover override that breaks the lock
  after a deadline.

### G6.1 — LD6: denominator redefinition breaks existing output contract [LD6]
LD6 says output denominator = `n`. The existing jewilo output is
`<approveCount>/<m>` — `src/bin/verifier_loop.rs:157,176` print
`"did not reach {}/{} consensus"` with `config.n, config.m` (n first, m
second), and the round-pass display is `m`-denominated ("2/2" = 2 of m=2).
Switching denominator to `n` silently changes the meaning of every existing
script/parser that treats `/X` as "X verifiers ran". For n=1, m=3 an APPROVE
would read "2/1" — a reader assumes 2 of 1, nonsense.
- Evidence: src/bin/verifier_loop.rs:157,176 (`config.n, config.m` order);
  turn2 output table uses "/2" where 2 = m.
- Mitigation: keep `/m` (total verifiers in the terminal phase) OR add an
  explicit `pipeline` segment prefix (e.g. `PL-D 2+1/2`) so the denominator's
  referent is unambiguous. Do not silently flip `/m` → `/n`.

### G7.1 — LD7: hash does not bind phase assignment; evaluate() has no phase filter [LD7]
`consensus::evaluate` takes a flat `verdicts: &[(String, VerdictRecord)]`
slice (src/consensus/mod.rs:151-160) with no phase parameter. LD7 says hash =
union of matching verdicts across all sub-phases, but nothing in the verdict
record or slot path records WHICH phase a verdict belongs to. LD16 role
prefixes (d1,s1) identify role, not phase — a smart slot s1 in Confirm vs a
smart slot s1 in Final collide. If a verifier (or a bug) registers a verdict
into the wrong slot during the wrong phase, evaluate() counting "all slots
under this round" will fold it into the hash. The hash proves verdict content
integrity but NOT pipeline-order integrity.
- Evidence: src/consensus/mod.rs:151-160 (no phase arg); LD16 (role prefix
  only); LD3 (sub-phases share one round).
- Mitigation: (a) add `phase` to the verdict slot path and to the
  `MatchingVerdict` hash input, or (b) enforce phase filtering at the call
  site by passing only the current phase's slice to evaluate() and document
  that the union is assembled by the caller (not by evaluate()).

### G8.1 — LD8: "global config" contradicts the existing per-goal config snapshot [LD8]
`goal::new` already snapshots the full `Config` into `goal.json` at NEW time
(src/goal/mod.rs:48-49 `config: store::Config`, line 94 `Config::load_in`,
line 101 stored in GoalRecord). The snapshot is the source of truth for
n/m/timeout for that goal's lifetime — that is the existing fail-closed
determinism guarantee. LD8 says pipeline config (escaT, dumpAdapter,
smartAdapter, confirmCount) is "global, NOT per-goal at NEW". If the runtime
reads the live global config.json for pipeline fields but the snapshot for
n/m, then editing config.json mid-goal changes ONLY pipeline behavior — a
half-snapshotted, non-deterministic hybrid. If instead the pipeline fields
are ALSO snapshotted, LD8's "global" is only about edit location, not read
location, and the decision text is misleading.
- Evidence: src/goal/mod.rs:48-49,94,101 (config snapshot at NEW);
  LD8 ("global. NOT per-goal at NEW time").
- Mitigation: state explicitly whether pipeline fields are snapshotted into
  goal.json (consistent with existing pattern) or read live (and accept
  mid-goal drift). Recommend snapshot for determinism parity.

## Rank 3 — Moderate (correctness/observability gaps, addressable)

### G4.4 — LD4: "2 consecutive" undefined across phase transitions and RESUMEs [LD4]
"Consecutive" is never defined. Does a PL-E Mixed-reject (which resets esca)
break the streak? Does an interrupted RESUME (Ctrl-C after Gate pass, before
Confirm) count as a Gate-pass-Confirm-reject? The counter is in state.json
(turn3), so it survives RESUME, but the definition of what increments it
across the PL-D→PL-E→PL-D boundary is ambiguous.
- Evidence: LD4 ("2 consecutive"); turn4 lifecycle (reset rules) — no
  definition of "consecutive" scope.
- Mitigation: define streak unit = "a completed PL-D invocation ending in
  Confirm-reject"; PL-E invocations never increment the PL-D streak.

### G5.3 — LD5: single-cmd wall-clock = Σ phase timeouts; no intermediate visibility [LD5]
Worst case m=2,k=1,escaT=2 reached: round N does Gate(2×1800)+Confirm(1800)
[esca=1] → RESUME → same [esca=2] → RESUME → Mixed(2×1800)+Final(1800).
That is 9 verifier-timeouts = ~4.5h for one logical approval, with A blocked
the whole time and no per-phase progress emitted (no AwaitingConfirmation
state per LD5). The outer agent cannot tell whether jewilo is hung vs working.
- Evidence: config verifierTimeoutSec=1800; LD5 (no intermediate state).
- Mitigation: emit per-phase progress to stderr / trace.jsonl (observe layer
  already exists) so A can distinguish progress from hang; document the
  wall-clock ceiling.

### G5.4 — LD5: no VERIFIER_LOOP_PHASE env; prompt note-collection collides by round [LD5]
`prompt::collect_prior_reject_notes` (called in run_round, per turn5) iterates
verdicts BY ROUND. LD3 puts all sub-phases under one round. So a smart-phase
verifier's prompt-build sees BOTH Gate-phase notes AND prior-round notes with
no way to distinguish them — turn5 hand-waves this as "a minor prompt-rendering
tweak" but the round-collision means the existing collect helper cannot filter
by phase without a new env var or path key. Also there is no
`VERIFIER_LOOP_PHASE` env (src/spawn/orchestrator.rs identity env list), so a
verifier backend cannot even self-report its phase.
- Evidence: src/spawn/orchestrator.rs (ENV_GOAL_ID/VERIFIER_ID/ROUND only, no
  PHASE); turn5 admission that APPROVE-vs-REJECT note surfacing is a delta.
- Mitigation: add `VERIFIER_LOOP_PHASE` env + phase subdirectory in the slot
  path; teach collect_prior_reject_notes to filter by phase.

### G6.2 — LD6: reject-path output ambiguous without knowing n [LD6]
"1/2" on a reject means "1 of m=2 approved, below n". But if n=1, "1/2"
would be a PASS. A reader/script seeing "1/2" cannot tell pass from reject
without also knowing n. The `+` segment count disambiguates pipeline path but
not pass/reject when the sum < n.
- Evidence: turn2 output table ("1/2" = "partial dump pass", reject).
- Mitigation: always print a pass/reject token alongside (e.g.
  `REJECT 1/2` / `APPROVE 2+1/2`), or use exit code + a JSON mode.

### G6.3 — LD6: phase composition not encoded (roles/adapters/m invisible) [LD6]
LD6 claims "Lets reader determine pipeline shape from output alone". But the
output only encodes per-segment APPROVE counts. "2+1/2" reveals neither m
(was Gate 2D or 3D with 1 null?) nor which adapters ran (dump=pi?
smart=hermes?). For audit/replay you still need goal.json + config. The
claim overstates what the string carries.
- Evidence: turn3 output examples (`1+2+1/2` for m=3 PL-E) — m is inferable
  only if you already know the floor/ceil rule AND that no nulls occurred.
- Mitigation: weaken the claim to "encodes path (PL-D vs PL-E) and per-phase
  approve counts", OR add the LD14 `pipeline` field to stdout, not just
  completion.json.

### G7.2 — LD7: sub-phase identity lost in hash (round_number only) [LD7]
Hash input includes `String(roundNumber)` = top-level round (src/consensus
mod.rs compute_hash). Sub-phases 1a/1b/1c are NOT in the hash input. Two
different sub-phase orderings that yield the same matching-verdict set
produce byte-identical hashes. Combined with G7.1 (no phase in slot path),
the hash cannot distinguish "Gate(d1,d2) then Confirm(s1)" from a hypothetical
re-ordering that happens to register the same three APPROVEs.
- Evidence: src/consensus/mod.rs compute_hash inputs (round, no sub-phase);
  LD3 (1a/1b naming) — never enters the hash.
- Mitigation: include a canonical phase-ordering string in the hash input, or
  rely on receiptHead (G7.3) to bind order — but only if receipt spans phases.

### G7.3 — LD7: receiptHead binding depends on receipt log spanning sub-phases (unverified) [LD7]
compute_hash includes `receiptHead` (chain tip of receipt log). The receipt
log (`src/receipt/mod.rs`) is a single per-goal chain keyed by seq, with no
phase concept. IF every verdict across all sub-phases is appended to the same
chain in registration order, receiptHead transitively binds phase order —
good. But this is ASSUMED, not verified: nothing in the findings proves the
pipeline calls `append_receipt` for Gate verdicts, then Confirm verdicts, in
order. If a phase skips the receipt append (e.g. a fast-path), receiptHead no
longer covers the full chain and G7.2's ambiguity becomes exploitable.
- Evidence: src/receipt/mod.rs (single chain, no phase field); findings never
  state receipt-append is mandatory per sub-phase.
- Mitigation: make append_receipt mandatory for EVERY verdict write across
  all sub-phases; add a test asserting receiptHead changes after each phase.

### G8.2 — LD8: shared store = shared pipeline policy (no multi-tenancy) [LD8]
`~/.verifier-loop/config.json` is one file for the whole store. Two outer
agents (or two projects) sharing the store cannot have different escaT /
adapter choices. The existing single-`backend` field already has this limit,
but the pipeline adds 4 more globally-enforced fields (dumpAdapter,
smartAdapter, confirmCount, escaT), widening the conflict surface.
- Evidence: src/store/config.rs (single Config, no per-goal override path);
  LD8 ("global").
- Mitigation: allow per-goal override via a `--pipeline-config` flag or a
  `pipeline.json` in the goal dir that supplements the global default; or
  document the single-policy-per-store limit explicitly.

### G8.3 — LD8: escaT=0 semantics undefined (disable vs always-on) [LD8]
turn3 defaults escaT=2 but never specifies escaT=0. `esca >= 0` is always
true → pipeline is PL-E from round 1. A user setting "escaT=0" intending
"disable escalation" gets the opposite (always-escalate). LD15 only addresses
m<2, not escaT=0.
- Evidence: turn3 config schema (escaT, no 0-handling); LD15 (m<2 only).
- Mitigation: define escaT=0 as "escalation disabled" (PL-D forever) and
  validate at config load.

### G8.4 — LD8: deny_unknown_fields makes config schema NON-rot-proof (tension with LD11) [LD8]
`Config` uses `#[serde(deny_unknown_fields)]` (src/store/config.rs) — the
canonical key set is closed; adding `dumpAdapter`/`smartAdapter`/
`confirmCount`/`escaT` requires a code change to the struct. LD11 claims
"concepts must be rot-proof" and LD8 says pipeline config is global, but the
delivery vehicle (config.json schema) is hardcoded and rejects unknown keys.
Adding a 5th phase or a new adapter knob = struct edit + redeploy, not a
config-only change. The "rot-proof" property holds for the Phase/Pipeline
abstraction but NOT for the config surface that feeds it.
- Evidence: src/store/config.rs `#[serde(deny_unknown_fields)]` + closed
  field list; LD11 (rot-proof claim).
- Mitigation: either (a) accept that the config schema is versioned code
  (keep deny_unknown_fields, bump on each addition), or (b) introduce a
  `pipeline: { ... }` sub-object with `deny_unknown_fields=false` so pipeline
  knobs can evolve without touching the core Config schema.

## Rank 2 — Minor (hygiene / edge cases)

### G5.5 — LD5: SIGINT mid-pipeline leaves orphaned partial state [LD5]
Single-cmd means one Ctrl-C can land between Gate-pass and Confirm-run. Gate's
d1/d2 APPROVE verdicts are already on disk under `rounds/1/`; esca was not
incremented (Confirm never ran). On next RESUME, round → 2, the round-1
verdicts are orphaned and the esca streak is lost. No cleanup/rollback is
defined for partial-pipeline interruption.
- Evidence: verdict write is immediate per slot (src/verdict/mod.rs);
  LD5 (no partial-state handling).
- Mitigation: on SIGINT, write a `pipeline-state.json` recording the phase
  reached so RESUME can resume the pipeline in-place instead of restarting.

### G6.4 — LD6: no machine-readable output mode [LD6]
Output is a human string (`2+1/2`). Pipeline path is encoded only in the `+`
segment count. Scripts must string-split on `+` and `/` to recover structure.
No `--json` flag specified; the existing `println!("{hash}")` (single line)
gives no phase breakdown to a parser.
- Evidence: src/bin/verifier_loop.rs:171,499 (println of hash only).
- Mitigation: add `--json` emitting `{pipeline, phases:[{role,count,approved}], n, m, verdict}`.

### G7.4 — LD7: `matching_verdicts` field semantics shift [LD7]
`CompletionRecord.matching_verdicts` (src/consensus/mod.rs) currently means
"APPROVE verdicts matching for THIS round". Under the pipeline it becomes
"all APPROVE verdicts across all sub-phases of the terminal round". The field
name no longer matches its content; auditors reading old vs new completion.json
files cannot tell from the schema alone whether the list is single-phase or
multi-phase.
- Evidence: src/consensus/mod.rs CompletionRecord; LD7 (union across phases).
- Mitigation: rename to `matching_verdicts_by_phase` or add a `phases: [...]`
  grouping; keep the flat list as a deprecated alias for back-compat.

### G8.5 — LD8: config drift mid-goal changes escalation behavior [LD8]
If LD8 means "read live global config" (see G8.1), editing escaT between
RESUME N and N+1 changes a goal's escalation threshold mid-lifecycle. A goal
one reject away from PL-E may silently never escalate (escaT raised) or
escalate early (escaT lowered). The esca counter is per-goal but the
threshold it is compared against is global — the comparison is non-monotonic.
- Evidence: LD8 (global); state.json esca is per-goal (turn3).
- Mitigation: snapshot escaT into state.json at NEW (resolve G8.1 first).

## Cross-cutting note (not a per-LD gotcha)

The single highest-leverage fix is **adding a `phase` dimension to the slot
path** (`rounds/<round>/<phase>/<vid>/`) + a `VERIFIER_LOOP_PHASE` env + a
`currentPhase` in state.json. It simultaneously resolves G5.1 (recovery),
G5.4 (prompt collision), G7.1 (hash phase binding), and G7.2 (sub-phase
identity in hash). LD3's "sub-rounds share one round" decision is the root
cause of four of the significant gotchas and should be revisited before
implementation.
