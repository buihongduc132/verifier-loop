## Rank 4 — Significant (must resolve before implementation)

### G-LD3-1: Letter-suffix round IDs break the `u32` round type across the whole codebase
**Applies to:** LD3
**Gotcha:** LD3 says sub-rounds are named `1a, 1b, 1c, 1d`. The findings present this as a
cosmetic display/naming choice ("Distinguishes sub-phases from top-level RESUME rounds"). It is
NOT cosmetic — the round identifier is a load-bearing `u32` type threaded through every
consensus/tamper/recovery primitive:

- `src/goal/mod.rs:66` — `StateRecord { current_round: u32 }` (state.json contract).
- `src/consensus/mod.rs:14` — hash input `String(roundNumber)` where roundNumber is `u32`; the
  `compute_hash(... round: u32 ...)` signature at `src/consensus/mod.rs:333-344` makes
  `"1a"` non-representable without a type change that alters the deterministic hash input
  format (and thus audit-recompute of every historical receipt).
- `src/verdict/mod.rs:139,151,159-164` — `verdict_path`/`pubkey_path`/`read_verdict` all key on
  `rounds/<round>/<verifierId>/` with `round: u32`. Sub-round dirs `rounds/1a/...` cannot exist
  under the current type.
- `src/verdict/mod.rs:207-212` — `mint_and_pin_pubkey(... round: u32)` + `verify_record` carry
  `round` into the signed/verified payload. Changing it to a string changes the signature domain.
- `src/spawn/orchestrator.rs:3uo` — `ENV_ROUND = "VERIFIER_LOOP_ROUND"` env var is
  `round.to_string()`; the spawned child (`jewije`) round-trips it back as a `u32` parse.

**Why missed:** turn2/turn3 treat the suffix scheme as a *display* convention ("it will be
1b 1c 1d or something") and never connect it to the on-disk `u32` contract. The "just another
round" framing (LD2) masks that a round is a typed value, not a label.

**Mitigation:** decide explicitly — either (a) keep `round: u32` and represent the pipeline
position in a *separate* axis (`phaseId`, `subRound` enum) so the round counter stays the
RESUME-counter; or (b) widen the round type to `String` everywhere and update the
completion-proof spec's hash-input clause (`String(roundNumber)` → string identity), accepting
that historical receipts computed under `u32` no longer re-derive under the new format.

### G-LD2-1: "Just another round" contradicts how `collect_prior_reject_notes` and `current_round` interact
**Applies to:** LD2
**Gotcha:** LD2 asserts the smart phase has "the exact same mechanic, lifecycle as a normal round."
But the note-chaining mechanic LD2 leans on (turn5's collapse argument) only works because
`collect_prior_reject_notes(root, goal_id, current_round)` iterates `rounds/<N>/` directories
with `N < current_round` (`src/prompt/mod.rs:559-577`):

```rust
let Ok(round) = name_str.parse::<u32>() else { continue; };
if round >= current_round { continue; }   // exclude current round
```

For the smart (Confirm) phase to see the dump (Gate) phase's notes, Gate and Confirm must be in
**different numeric rounds**. But within ONE `jewilo NEW` invocation they are the same
`current_round` value (state.json is only incremented on `RESUME`, `src/goal/mod.rs:144`). So
the two possibilities are both broken:

- If sub-phases share `current_round` → Confirm sees nothing (Gate is "current", excluded).
  OT7-collapse argument in turn5 silently fails for the *within-invocation* dump→confirm handoff.
- If sub-phases increment `current_round` → the outer agent's `RESUME N+1` on rejection now
  collides with the internal counter; the user-visible round number drifts from the
  `state.json` counter, and `round_recover::status` (which calls `goal::current_round`) reports
  the wrong round.

**Why missed:** turn5's collapse ("each round will always see the PREVIOUS one") is correct
across RESUME boundaries but never verified for the *within-invocation* phase boundary, which is
exactly the case LD2 introduces.

**Mitigation:** extend `collect_prior_reject_notes` to walk a *phase-ordered* history (not just
`round < current_round`), OR explicitly bump `current_round` per phase and document that RESUME
after a sub-phase-reject targets the post-bump counter.

### G-LD11-1: `Config` uses `deny_unknown_fields` — adding `dumpAdapter/smartAdapter/confirmCount/escaT` is a breaking on-disk change
**Applies to:** LD11
**Gotcha:** `src/store/config.rs:42` declares `#[serde(default, deny_unknown_fields)]`. The
"closed canonical key set" is a deliberate tamper guard (test at `src/store/config.rs`:
`config_rejects_unknown_key_at_parse_time`). Two consequences the rot-proof claim ignores:

1. **Forward-only migration:** existing `config.json` files in the wild still parse (defaults
   fill the new fields), but a user who copies an old config into a new store with the new fields
   AND a legacy key will get a parse error with no migration story. turn3's 4-field schema
   addition is presented as "no schema rewrite" — it is a schema extension that must be tested
   against the closed-set invariant.
2. **Single `backend` field now ambiguous:** the existing `Config.backend: String`
   (`src/store/config.rs`) is the ONE adapter the current round uses. LD11 says "D and S are
   adapter refs" — two adapters. The relationship between `backend` (legacy, single) and
   `dumpAdapter`+`smartAdapter` (new, dual) is unspecified: is `backend` deprecated, aliased to
   `dumpAdapter`, or a fallback? A goal created under a `backend`-only config and then resumed
   under a `dumpAdapter`-only config has undefined behavior. The goal.json config snapshot
   (`GoalRecord.config: store::Config`, `src/goal/mod.rs:49`) freezes whichever shape was active
   at NEW — so the snapshot can carry a config the running binary no longer understands uniformly.

**Why missed:** turn3 lists the 4 new fields as "everything else is computed" but never addresses
the existing `backend` field or the `deny_unknown_fields` invariant it must coexist with.

**Mitigation:** explicitly specify `backend` semantics under the new schema (deprecate-and-alias
to `dumpAdapter`, or reject if both set); add a migration/compat test asserting an old-shape
config still round-trips and a mixed-shape config fails closed with a clear message.

### G-LD11-2: `SpawnInput` carries a single `adapter` — the pipeline needs per-phase adapter selection
**Applies to:** LD11
**Gotcha:** `src/spawn/orchestrator.rs` `SpawnInput<'a> { ... pub adapter: &'a acp::Adapter }`
is a single borrow. `spawn_round`/`spawn_resume` are called once per round with one adapter for
all `m` slots. LD11's "Phase = {role, count, threshold}" implies a Mixed phase has BOTH a dump
adapter AND a smart adapter within the same spawn call. This is not expressible in the current
shape without either:

- calling `spawn_round` twice (once per role) and merging the gathered runs — but `run_round`
  (`src/bin/verifier_loop.rs:248`) drives a single spawn→gather→evaluate cycle, so the
  "Vec<Phase> executor" turn3 sketches needs a new orchestration layer that selects the adapter
  per slot index; OR
- extending `SpawnInput` to an `adapters: Vec<Adapter>` parallel to slot indices — which breaks
  the per-verifier-adapter spec (`verifiers[].adapter`) compatibility claim in `references.md`.

**Why missed:** turn3 says "the executor runs `Vec<Phase>` sequentially" as if `spawn_round`
already supports heterogeneous adapters per slot. It does not — the existing per-slot adapter
machinery (`per-verifier-adapter` change, referenced in `references.md`) is a different config
surface (`verifiers[]`) than the proposed `dumpAdapter`/`smartAdapter` pair.

**Mitigation:** reconcile the three adapter config surfaces — legacy `backend`, per-slot
`verifiers[].adapter`, and proposed role-derived `dumpAdapter`/`smartAdapter` — into one
precedence rule before claiming the executor is generic.

## Rank 3 — Moderate (should resolve, has workarounds)

### G-LD3-2: `round_recover::status` and `round_recover::recover` are round-`u32`-hardcoded
**Applies to:** LD3 (and LD2)
**Gotcha:** `src/round_recover/mod.rs:183,322` reads `goal::current_round(root, goal_id)` and
builds `rounds/<round>.to_string()` directory paths; the slot enumeration
(`for i in 0..config.m { verifier_id(i) }` at `src/round_recover/mod.rs:200-219`) assumes
`m` uniform slots named `v1..vm`. Under the pipeline:

- `current_round` (after G-LD3-1) may be a letter-suffixed string → `round.to_string()` no
  longer resolves the right directory.
- slot enumeration assumes one adapter / `v{i+1}` ids, but LD16 introduces role-prefixed ids
  (`d1,d2,s1,s2`) and Mixed phases have heterogeneous slot counts. `STATUS` / `RECOVER` on a
  partially-run pipeline will miscount slots and report a false "needs=Resume" or wrong
  `raw_approve_count`.

**Why missed:** the round-recovery module is never mentioned in the turn files. references.md
notes "esca counter would join `current_round`" but does not surface that RECOVER/STATUS
hardcode both the round type and the `v{i+1}` slot naming.

**Mitigation:** RECOVER/STATUS must learn about the phase axis (which sub-phase is in-flight,
what its slot composition is) — either by reading a per-goal pipeline-state file or by making
the slot enumeration config-derived rather than `v1..vm`.

### G-LD7-context: canonical-JSON sort tie when `s1` approves in both Confirm and Final
**Applies to:** LD11 (the rot-proof / "hash over union of verdicts" assumption inherited from
LD7 and turn3's hash section)
**Gotcha:** `canonical_matching_json` sorts `matching_verdicts` ascending by `verifierId`
(`src/consensus/mod.rs:237,277`). Rust's `sort_by` is stable, so two entries with identical
`verifierId="s1"` (one from Confirm phase 1b, one from Final phase 1d — both APPROVE, both
contributing to the union per LD7) keep their *insertion* order, not a deterministic key order.
Insertion order is an artifact of how the union is built (phase order). This is fragile:

- Two correct implementations that build the union in different orders (e.g. Final-before-Confirm
  vs Confirm-before-Final) produce *different* canonical JSON → different completion hash.
- An auditor re-deriving the hash from `completion.json`'s `matchingVerdicts` array gets whatever
  order was serialized, which must byte-match the original — but the spec gives no rule for
  breaking the tie.

**Why missed:** LD7's "union of matching verdicts across all sub-phases" assumes
`verifierId` is unique across the union. LD16 (`d1,d2 / s1,s2`) makes `s1` REUSE across
Confirm and Final — the collision is created by LD16 and never reconciled with LD7's sort rule.

**Mitigation:** either namespace verifierIds by phase (`s1c` for Confirm, `s1f` for Final), or
add a deterministic tie-breaker (phase index, then `registeredAt`) into `canonical_matching_json`
and pin it with a test.

### G-LD11-3: "All counts/thresholds configurable" is only half-true — the escalation TRIGGER is structural
**Applies to:** LD11
**Gotcha:** LD11 says "compositions config-derived" and turn3 promises rot-proof concepts. But
the escalation RULE itself (`esca ≥ escaT` AND the trigger condition `dumpPass ∧ smartReject`) is
hardcoded in LD4 — only the *threshold* `escaT` is configurable. The trigger predicate is not
configurable: a user cannot express "escalate after dumpReject∧smartPass" or "escalate on any 2
consecutive non-unanimous rounds" without a code change. So "rot-proof" holds for the *values*
(n, m, escaT, confirmCount) but not for the *policy shape*.

**Why missed:** turn3 conflates "configurable numbers" with "rot-proof concepts." The Phase /
Pipeline abstraction is rot-proof for *adding phases*, but the *transition rule* between PL-D and
PL-E is a fixed predicate, not a config-derived transition.

**Mitigation:** either narrow the rot-proof claim to "phase composition is rot-proof; the
escalation predicate is a fixed design choice" OR make the trigger a config predicate
(`escalationTrigger: "dumpPassSmartReject" | "anyReject" | ...`). The former is honest; the
latter is more flexible but adds a config surface to maintain.

### G-LD2-2: `run_round`'s goal-lock + cooldown + health interaction with a multi-phase invocation
**Applies to:** LD2
**Gotcha:** `src/bin/verifier_loop.rs:11X,3vd` acquires the exclusive `GoalLock` for the whole
round and `warn_if_round_is_recoverable` runs before spawn. Under LD2 + LD5 (single cmd, all
phases), the lock is held across Gate→Confirm→(possibly Mixed→Final) — potentially 4 spawn/gather
cycles. Two interactions missed:

1. **Cooldown fan-in:** `src/health/` trips cooldown after >3 unhealthy events in 1h. A dump
   verifier crash in the Gate phase increments the unhealthy counter; if the pipeline then runs
   the Confirm phase in the same invocation, a single bad goal can burn through the cooldown
   budget 4× faster than today. references.md flags "dumpers crashing trips cooldown, which
   blocks the smart phase too" as an "open interaction" but it is never resolved.
2. **Lock duration:** `GoalLock` is advisory (flock). A 4-phase invocation holding it for
   `4 × verifierTimeoutSec` (default 1800s = 2h) blocks any concurrent `RECOVER`/`STATUS`
   probing of the goal for the entire pipeline. The round-recovery SHAPE-1 design exists
   precisely because long-held rounds need out-of-process probing — a 4× longer hold makes that
   worse, not better.

**Why missed:** turn2 says "Same spawn/gather/evaluate/lifecycle as a normal round" per phase,
but never sums the lock-hold or cooldown-budget across the phases of one invocation.

**Mitigation:** either release/reacquire the lock between phases (allows RECOVER between
phases) OR document that the pipeline invocation is uninterruptible for up to
`phases × verifierTimeoutSec` and that cooldown thresholds may need rescaling.

## Rank 2 — Minor (naming/UX, low blast radius)

### G-LD12-1: `esca` vs `escaT` differ by one trailing char — typo-prone, grep-hostile
**Applies to:** LD12
**Gotcha:** LD12 renames `Esc→esca` and `EscT→escaT` to dodge keyboard-Esc confusion. The new
pair `esca` / `escaT` introduces a *new* confusion: they differ by exactly one trailing capital
`T`. In code (`if esca >= escaT`), a typo (`esca` ↔ `escaT`) is a silent logic bug (compare
counter to counter, or threshold to threshold) that compiles and passes type-check. Grepping for
`esca` matches both; grepping for `escaT` requires care. The keyboard-Esc problem is solved but a
read/edit-error problem is created.

**Why missed:** turn4 treats the rename as a pure win ("rename only, outputs unchanged") with no
consideration of the new pair's distinguishability.

**Mitigation:** use a more separable pair — `escaCount` / `escaThreshold`, or `escaN` /
`escaT` if brevity matters. At minimum add a unit test that the two fields cannot be
transposed without a parse error or assertion.

### G-LD12-2: `escaT` is non-idiomatic Rust and awkward in camelCase JSON
**Applies to:** LD12
**Gotcha:** The JSON field is `escaT` (lowercase word + capital T). In Rust this becomes
`esca_t: u32` with `#[serde(rename = "escaT")]`. Mid-word capital letters in camelCase
(`escaT`, not `escaThreshold`) are unusual — most JSON conventions use either full camelCase
(`escaThreshold`) or full lowercase (`escat`). The chosen shape reads as a typo for "esc at" or
"escat" to anyone who did not see the rename rationale. Existing config fields follow strict
camelCase (`maxTurn`, `gitDiffMaxChars`, `verifierTimeoutSec`); `escaT` breaks that pattern.

**Why missed:** turn4 does not review the rename against the existing config field naming
convention.

**Mitigation:** use `escaThreshold` (matches existing camelCase convention) or document the
deviation explicitly in the config spec.

### G-LD1-1: "Cost is not a consideration" leaves the D/S distinction semantically undefined
**Applies to:** LD1
**Gotcha:** LD1 strips the cheap/expensive framing but keeps the D/S *names*, which carry an
implicit capability hierarchy ("dump" = superficial, "smart" = thorough). Once cost is off the
table, what *observable property* distinguishes D from S? Two readings diverge:

- If D and S are just "two adapter slots" with no implied capability difference, then the names
  are misleading and LD4's escalation rule (`dumpPass ∧ smartReject`) has no justification —
  why does smart's reject override dump's pass if they are peers?
- If S is genuinely "stronger" than D, then a quality/capability axis IS being tracked (just not
  a cost axis), and LD1's "cost is NOT a consideration" is incomplete — it should say "cost is
  not a consideration, but capability ordering is, and S ≥ D by assumption."

The escalation logic (LD4), the existence of a Final smart-after-Mixed phase, and the whole point
of running a smart Confirm after a dump Gate all *presuppose* S ≥ D in detection power. LD1's
wording hides that presupposition.

**Why missed:** turn2 reframe swaps "cheap/expensive" for "dump/smart" as a pure vocabulary
change without stating what (if anything) the new vocabulary commits to beyond a label.

**Mitigation:** add one clause to LD1: "D and S are capability-ordered labels (S verifies at
least as strictly as D); cost is not the axis, but the S ≥ D capability assumption is load-bearing
for LD4's escalation predicate." Or, if S ≥ D is NOT assumed, redesign LD4 to not depend on it.

## Rank 1 — YAGNI (noted, likely not worth acting on)

### G-LD11-4: "Adding a 5th phase type later = one derived rule" is speculative future-proofing
**Applies to:** LD11
**Gotcha:** turn3 justifies the `Vec<Phase>` executor partly by "adding a 5th phase type later =
add one derived rule, not a schema rewrite." There is no stated 5th-phase need; the 4 phases
(Gate/Confirm/Mixed/Final) already cover the LD4 escalation ladder. Designing for a hypothetical
5th phase now risks over-abstraction (a `Phase` struct generic enough for unknown future phases
is harder to reason about than 4 named phases).

**Why missed:** this is the classic YAGNI trap dressed as "rot-proof."

**Mitigation:** keep `Vec<Phase>` only if it falls out naturally from the LD4 logic; do not
pre-generalize for a 5th phase that has no requirement.

## Residual risks (for parent)

- The Rank-4 items (G-LD3-1, G-LD2-1, G-LD11-1, G-LD11-2) are mutually reinforcing: the round
  type change (G-LD3-1) is a prerequisite for the note-chaining fix (G-LD2-1) and the
  RECOVER/STATUS fix (G-LD3-2). They should be designed together, not piecemeal.
- None of the gotchas invalidate the locked decisions; they surface unspecified or
  under-specified consequences. The LDs are still defensible IF the mitigations are folded into
  the OpenSpec proposal (OT6, still deferred).
- No source files were modified — read-only review.
