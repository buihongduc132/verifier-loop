## Rank 4 — Significant

### G1 — LD16: d/s counter scope undefined → within-invocation verifierId collisions

**Gotcha.** LD16 says dump slots = `d1,d2,…` and smart slots = `s1,s2,…`, claiming "Unique + stable across phase compositions". It never specifies whether the per-role counter **restarts per phase** or **continues across phases within an invocation**.

- If per-phase-restart (the natural reading of "smart-phase slots = s1,s2,…"):
  - Gate (d1,d2) → Mixed (d1) **collides** on `d1`.
  - Mixed (s1,s2 for m=3) → Final (s1) **collides** on `s1`.
- The collision lands in the **same invocation's hash input**: LD7 says hash input = `canonicalJSON(matchingVerdicts sorted by verifierId)` across all sub-phases. Two entries with `verifierId: "d1"` (or `"s1"`) appear in the same array — the `Unique` claim is false.
- Pubkey pinning (`add-verifier-tamper-hardening`) keys on verifierId. Mixed's `d1` inheriting Gate's `d1` pubkey means a Mixed verifier signs with Gate's pinned key — cross-phase key reuse the findings never analyzed.
- If the counter instead continues (Gate d1,d2 → Mixed d3), the findings never said so and the LD16 prose contradicts that reading.

**Severity.** 4 — affects hash determinism semantics, pubkey identity, and the literal "Unique" claim. Implementation cannot proceed without resolving counter scope.

**Mitigation.** Define counter scope explicitly. Two clean options:
1. **Per-invocation monotonic**: d1..d{floor(m/2)} for Gate; Mixed continues from d{m+1}..d{m+floor(m/2)}; smart continues s1..s{k} for Confirm, s{k+1}..s{k+ceil(m/2)} for Mixed, s{k+1} for Final. No collisions, but ids grow with phase count.
2. **Per-phase with phase qualifier**: `Gd1`, `Md1`, `Cs1`, `Fs1` — phase prefix disambiguates. Breaks the "role-transparent in the receipt hash" clause of LD16 but fixes uniqueness.

Either way, LD16 must be amended with an explicit scope rule before implementation.

**Evidence.** `2026-07-20-locked-decisions.yaml` LD16 tradeoff; `src/consensus/mod.rs` MatchingVerdict + hash formula (verifierId is the only slot discriminator); `src/spawn/orchestrator.rs:41-43` current `verifier_id(idx)` uses a single monotonic `v{idx+1}` — the new d/s scheme has no analogous rule for cross-phase continuity.

### G2 — LD15: esca counter time-bomb on m bump (ignored-but-accumulated esca fires silently)

**Gotcha.** LD15 says "when m < 2, escaT is IGNORED — pipeline stays PL-D forever". But the esca lifecycle (turn3) still increments esca on every `Gate-pass + Confirm-reject`. The findings never said whether esca is **reset, frozen, or merely ignored** while m<2.

Scenario:
1. Config: m=1, escaT=2. Goal runs 50 PL-D rounds; esca accumulates to, say, 15 (many Confirm-rejects).
2. Operator bumps m to 2.
3. Next round: m=2, esca=15 ≥ escaT=2 → **immediately escalates to PL-E** on the very next invocation.

The operator sees a "normal" m=2 run suddenly produce a Mixed phase with no prior Gate-pass+Confirm-reject pattern in the m=2 regime. The escalation is silent — no warning, no reset, no transition event. The findings treat "ignored" as if it meant "doesn't matter", but the counter keeps ticking.

**Severity.** 4 — silent behavior change across a routine config edit; violates operator expectation that escalation reflects recent behavior.

**Mitigation.** Pick one and codify:
- **Reset on m<2**: when m<2, set esca=0 on every invocation (prevents accumulation).
- **Freeze on m<2**: don't increment esca while m<2 (esca stays at the value it had when m was last ≥2).
- **Reset on m transition**: when m crosses from <2 to ≥2, reset esca=0 (one-shot guard).

The first is simplest. Whichever is chosen, LD15 must be amended to state it explicitly.

**Evidence.** `2026-07-20-locked-decisions.yaml` LD15 tradeoff (only discusses m=1 degeneracy, not esca lifecycle); turn3 esca lifecycle (`esca++` on Gate-pass+Confirm-reject, unconditional); `src/goal/mod.rs:66` StateRecord holds `current_round` — esca would live alongside it and persist across config changes.

## Rank 3 — Moderate

### G3 — LD9: odd m makes dump approvals mathematically unnecessary for Mixed to pass

**Gotcha.** For any odd m, `ceil(m/2) = (m+1)/2 > floor(m/2) = (m-1)/2`. With threshold n preserved from Gate, if `n ≤ ceil(m/2)` (the common case — e.g., m=3 n=2 → ceil(3/2)=2 ≥ n), the smart side alone can pass Mixed without any dump approval. For m=5 n=3: Mixed = 2D+3S, and 3S alone hits threshold.

The findings' table shows the numbers (m=3 → 1D+2S) but never analyzed the **pass-implication**: dump votes in Mixed become purely advisory for all odd m. This contradicts the "Mixed voice" intent from LD4 ("half-half, round up") — the user likely expected dump to be a *swing* vote, not a bystander.

**Severity.** 3 — semantic gap between the "mixed" intent and the math; not a correctness bug but a design-intent mismatch.

**Mitigation.** Either:
- Acknowledge explicitly in LD9 that for odd m, dump is advisory-only at pass time (document the asymmetry).
- Add a **dual-threshold** rule for Mixed: require ≥1 dump approval AND ≥1 smart approval (prevents smart-only pass). This preserves the mixed intent but adds a new rule.
- Require even m for PL-E activation (reject config where m is odd and escaT>0).

### G4 — LD9 / LD10: m is not frozen at NEW → receipt non-determinism under config mutation

**Gotcha.** LD9 says Mixed composition is "dynamic per m" and LD8 places config in global `config.json` (mutable). LD10 makes Gate count = m. Neither LD says whether m is **snapshotted into the goal at NEW** (like the per-verifier-adapter config snapshot in `goal.json`) or **re-read from current config each invocation**.

If re-read:
- A goal created at m=2 escalates to Mixed (1D+1S) in round 5.
- Operator bumps m to 4 mid-lifecycle.
- Round 6 Mixed = 2D+2S.
- Audit recompute of round 5's receipt using current config yields 2D+2S ≠ 1D+1S → hash mismatch → receipt unverifiable.

If snapshotted:
- LD9/LD10 must explicitly say "m is frozen into goal.json at NEW time, like adapter config".
- The findings reference per-verifier-adapter snapshotting but never extend that rule to m/n for the new pipeline.

**Severity.** 3 — affects audit recompute determinism; silent breakage unless codified.

**Mitigation.** Add to LD9/LD10: "m and n are snapshotted into the goal record at NEW time. Pipeline composition for every round of that goal is derived from the snapshot, not live config." This matches the existing adapter-snapshot pattern.

**Evidence.** `src/goal/mod.rs` goal record; per-verifier-adapter change already snapshots adapter config into goal.json (cited in turn1); LD8 (global config) + LD9 ("dynamic per m") together imply re-read unless frozen.

### G5 — LD10: n > m is an impossible config that creates a perpetual-REJECT loop

**Gotcha.** LD10 says "threshold n + count m both configurable" with no constraint. If a user sets n=3, m=2: Gate needs 3 approvals from 2 verifiers → impossible → Gate always rejects. With LD13 (hard reject → A RESUMEs), this becomes an infinite RESUME loop. esca never increments (Gate never passes, so the esca++ trigger never fires), so there's no escalation escape either. The goal is permanently stuck.

**Severity.** 3 — silent misconfig with no recovery path other than manual goal abandonment.

**Mitigation.** Add config validation: reject `n > m` at parse time (fail-closed, same as malformed JSON per `src/store/config.rs:36` `deny_unknown_fields`). Error message: `"n (threshold) must be ≤ m (verifier count)"`. This is a 3-line addition to the Config loader.

**Evidence.** `src/store/config.rs:39-41` `pub n: u32`, `pub m: u32` with no cross-field validation; `deny_unknown_fields` only rejects unknown keys, not invalid values.

### G6 — LD16: role-prefix couples hash to role naming, tension with LD11 rot-proof intent

**Gotcha.** LD11 says "concepts must not rot — adapter names not hardcoded". LD16 bakes the role initial (`d` for dump, `s` for smart) into the verifierId, which is a hash input (`src/consensus/mod.rs` MatchingVerdict.verifier_id). If the role labels are ever renamed (dump→fast, smart→thorough), every historical receipt's verifierId changes (`d1→f1`), and the hash can no longer be recomputed from the original inputs.

The findings' LD16 tradeoff acknowledges "breaks current v{i+1} convention" but doesn't note that it also makes the hash **coupled to the English role labels** — exactly the rot LD11 was meant to prevent.

**Severity.** 3 — real tension between two locked decisions; not a bug today but a future rename breaks audit.

**Mitigation.** Either:
- Use role-neutral ids (e.g., monotonic `v1..v{total}` per invocation, with role recorded as metadata only — not in the hash input). This restores LD11 compatibility but loses LD16's "role-transparent in receipt" property.
- Accept the coupling and explicitly note in LD16 that role labels are **frozen** (renaming them breaks historical receipt verification). Add a "role rename = new pipeline version" rule.

### G7 — LD16: migration of existing v-namespace goals is unaddressed

**Gotcha.** Current `verifier_id(idx)` emits `v{idx+1}` (`src/spawn/orchestrator.rs:41-43`). LD16 switches to `d*`/`s*`. The findings' tradeoff note mentions "breaks current `v{i+1}` convention" but never addresses:

- In-flight goals with `rounds/<round>/v1/verdict.json` become orphaned when the binary switches to `d1`/`s1`.
- A RESUME on an existing goal after the binary upgrade would look for `d1` verdicts, find none, and treat all slots as null → fail-closed.
- No migration path (rename v→d dirs? shim function that maps old→new? version flag in state.json?).

**Severity.** 3 — deployment hazard for any store with live goals at upgrade time.

**Mitigation.** Pick one:
- **Migration script**: on upgrade, rename `rounds/*/v{i}` → `rounds/*/d{i}` for all goals.
- **Compatibility shim**: `verifier_id(idx)` checks if `v{idx+1}` dir exists for the current round; if yes, uses `v*`; otherwise uses `d*`/`s*`. Per-round detection.
- **Version gate**: state.json gains a `verifier_id_version` field; old goals use v-namespace, new goals use d/s.

**Evidence.** `src/spawn/orchestrator.rs:41-43` `fn verifier_id(idx) -> String { format!("v{}", idx + 1) }`; `src/spawn/orchestrator.rs:486` `let vid = verifier_id(i); let vdir = rounds_dir.join(&vid);`.

## Rank 2 — Minor

### G8 — LD10: n = 0 creates a vacuous-pass Gate

**Gotcha.** n=0, m≥1: Gate threshold is 0 approvals needed → Gate passes unconditionally → always runs Confirm. The findings never considered n=0 as a degenerate "skip gate" config. May be intentional (always-smart pipeline) but is not validated or documented.

**Severity.** 2 — edge case with a plausible legitimate use (skip-gate) but no validation or documentation.

**Mitigation.** Either allow n=0 explicitly (document as "skip-gate mode") or reject n=0 at config parse time. If rejected, add `n ≥ 1` validation alongside G5's `n ≤ m` validation.

---

### G9 — LD10: output sum > denominator for m > n (e.g., "4/2")

**Gotcha.** LD6 output format `<sum>/<n>`. For m=3 n=2, a full Mixed+Final pass yields `"1+2+1/2"` (sum=4, denom=2). Reads as 200% consensus. The findings show this exact example without flagging that it may confuse audit tooling or humans parsing the receipt.

**Severity.** 2 — cosmetic/parseability issue; not a correctness bug.

**Mitigation.** Document that the denominator is threshold (not count) and sum can exceed it for m>n. Alternatively, change format to `<sum>/<m>` (count) with threshold noted separately, or add a pipeline marker: `"1+2+1/2[PL-E]"`.

---

### G10 — LD15: m = 0 is not covered by the m < 2 analysis

**Gotcha.** LD15 says "when m < 2, pipeline stays PL-D forever (Gate m-dump → Confirm k-smart)". For m=0: Gate has 0 dump verifiers. The pipeline description assumes m≥1 (at least one dump slot). At m=0, "Gate 0-dump" is ill-defined — does it pass vacuously (0≥n only if n=0) or error? The findings analyzed m=1 but never m=0.

**Severity.** 2 — degenerate config; unlikely in practice but the decision's wording is incomplete.

**Mitigation.** Add to LD15 (or a new LD): "m ≥ 1 is required. m = 0 is a config validation error." Or explicitly handle m=0 as a no-verifier mode.

---

### G11 — LD15: stderr warning fires on every invocation (warning fatigue)

**Gotcha.** LD15 says "a stderr warning is emitted if escaT > 0 while m < 2". With a persistent intended config of m=1 + escaT=2, the warning fires on every NEW and every RESUME — potentially hundreds of times for a long-running goal. No once-per-config or once-per-goal dedup.

**Severity.** 2 — UX noise; may cause operators to suppress stderr or ignore real warnings.

**Mitigation.** Emit the warning once per config-load (not per invocation), or write it to a config-validation log at startup, or store a "warned" flag in state.json and only warn once per goal.

---

### G12 — LD9: m = 0 produces empty Mixed/Gate (0D + 0S)

**Gotcha.** floor(0/2) = 0, ceil(0/2) = 0. Mixed = 0D + 0S. Gate = 0D. The findings analyzed m=1 but never m=0. At m=0 the formula produces an empty pipeline with no verifiers at all.

**Severity.** 2 — same root cause as G10; degenerate config.

**Mitigation.** Same as G10: require m ≥ 1 at config validation.

## Residual risks

- **Counter scope (G1)** is the most urgent — implementation cannot start without resolving it.
- **esca time-bomb (G2)** is the highest-severity runtime gotcha — silent misbehavior on config edit.
- **m-freeze (G4)** affects audit determinism — must be codified before any receipt is written.
- **Migration (G7)** is a deployment hazard — must be planned before the binary ships.
